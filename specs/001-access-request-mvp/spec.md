# 功能规格：AccessFlow MVP

**功能目录**：`001-access-request-mvp`

**创建日期**：2026-08-31

**状态**：草案

**输入**：创建企业内部访问权限申请与审批系统的 MVP。

## Clarifications

### Session 2026-08-31

- Q: 在不实现登录系统的前提下，MVP 应如何切换演示身份，并确定 Requester 与 Approver？ → A: 提供多个
  可切换的预置演示员工身份；`DemoUser` 不保存互斥或永久角色。对于任一申请，`requesterId` 等于当前员工 ID
  时该员工是 Requester，`approverId` 等于当前员工 ID 时该员工是 Approver。同一员工可以查看自己提交的申请，
  也可以审批分配给自己的其他申请，但不得审批自己的申请。
- Q: 用户创建申请或完成审批后，这些业务数据应在多大范围内持续存在？ → A: 申请、状态变化和审批记录
  必须在同一浏览器演示环境中持续存在，由所有预置身份共享，并在刷新、关闭后重新打开及切换身份后保留；
  不要求跨浏览器或跨设备共享。
- Q: MVP 应采用哪一种可验收规则，根据目标资源和权限级别确定风险等级？ → A: 每个允许的“目标资源＋
  权限级别”组合必须直接对应唯一的 `Low`、`Medium` 或 `High` 风险等级；未定义组合不能提交。
- Q: MVP 中的“访问期限”应具体表示什么，并采用哪一组有效性规则？ → A: 使用单一访问截止日期；访问在申请
  被批准后开始生效，到截止日期结束。截止日期必须晚于提交日和批准日，已到期的待审批申请不能批准。
- Q: 新创建的申请应如何从预置审批候选员工中确定唯一的负责审批人？ → A: 每个目标资源预先关联有顺序的
  审批候选员工列表；创建申请时分配给第一位不是申请人的员工，没有合格员工时阻止提交。预置 Demo 数据和
  资源分配必须保证正常演示流程始终存在非申请人的可用审批员工。

## 用户场景与测试（必填）

### 用户故事 1：创建权限申请（优先级：P1）

申请人需要为目标资源提交一份信息完整的访问权限申请，以便把申请原因、权限范围和访问截止日期纳入
统一、可追踪的审批流程。创建成功后，申请人需要立即知道申请已进入待审批状态。

**优先级说明**：创建申请是整个流程的起点；没有有效申请，后续查询、详情和审批均无法产生业务价值。

**独立测试**：使用已知的申请人身份，填写一份有效申请并提交；无需完成审批即可验证申请被创建、
状态为 `Pending`，并能从列表和详情中找到。

**验收场景**：

1. **前提**申请人已填写有效的目标资源、权限级别、访问截止日期和申请原因，**当**提交申请，
   **则**系统创建一条状态为 `Pending` 的申请，并提供明确的成功反馈和查看申请的入口。
2. **前提**一个或多个必填字段缺失或访问截止日期不晚于提交日，**当**申请人尝试提交，
   **则**系统阻止提交，明确标识每个无效字段，并保留已填写的有效内容。
3. **前提**申请正在提交，**当**申请人继续操作提交控件，
   **则**系统明确显示进行中状态，并阻止生成重复申请。
4. **前提**提交失败且允许重试，**当**系统返回失败结果，
   **则**申请保持未创建，申请人看到明确的失败原因或可理解提示、保留的表单内容和重试入口。
5. **前提**申请已创建成功，**当**用户刷新页面、关闭后重新打开或切换演示身份，
   **则**该申请及其当前状态仍然存在，并按照当前身份的可见范围展示。
6. **前提**申请人选择了一个已定义的目标资源与权限级别组合，**当**提交申请，
   **则**申请的风险等级与该组合预先指定的唯一风险等级一致；未定义组合不能提交。
7. **前提**目标资源的有序审批候选员工列表中存在至少一位不是申请人的员工，**当**提交有效申请，
   **则**申请被分配给列表中第一位符合条件的员工；没有合格员工时阻止提交并明确说明原因。

---

### 用户故事 2：查找和浏览权限申请（优先级：P1）

申请人需要查看自己的申请，审批人需要查看分配给自己的申请。用户需要通过搜索、状态筛选、风险筛选
和分页快速定位目标申请，并能通过刷新、前进后退或分享页面地址恢复相同的查询状态。

**优先级说明**：统一且可恢复的列表是追踪申请状态和进入后续操作的主要入口。

**独立测试**：准备跨申请人、资源、状态和风险等级的申请数据，仅通过列表完成搜索、组合筛选、分页，
并验证刷新、浏览器前进后退及复制地址后仍恢复相同结果。

**验收场景**：

1. **前提**当前用户的可见范围内存在申请，**当**打开申请列表，
   **则**每条申请显示申请人、目标资源、申请权限、风险等级、当前状态和创建时间。
2. **前提**存在多个申请，**当**用户输入申请人或资源名称并组合状态、风险等级筛选，
   **则**列表只展示同时符合全部有效条件的申请，并提供分页导航。
3. **前提**用户已设置搜索词、筛选条件和页码，**当**刷新页面、使用浏览器前进后退，
   或在另一页面打开复制的当前地址，**则**恢复相同的查询条件和对应结果页。
4. **前提**当前查询没有匹配申请，**当**查询完成，
   **则**页面显示明确的空状态，说明没有匹配结果，并提供清除或调整查询条件的途径。
5. **前提**列表加载失败且允许重试，**当**错误发生，
   **则**页面显示明确错误状态、保留当前查询条件并提供重试入口。
6. **前提**存在多个预置演示员工身份，**当**用户切换当前身份，
   **则**列表和可用操作立即按照新身份与每条申请的关系更新；同一员工能够同时看到自己提交的申请和分配给
   自己的其他申请。

---

### 用户故事 3：查看申请详情（优先级：P1）

用户需要查看某条申请的完整业务信息和审批记录，以理解申请内容、风险、当前状态及已发生的审批结果。

**优先级说明**：详情是申请人与审批人核实信息、理解状态以及作出审批决定的共同依据。

**独立测试**：使用一条已存在的申请直接进入详情，核对所有规定信息，并验证刷新页面后仍显示同一申请。

**验收场景**：

1. **前提**用户有权查看一条已存在的申请，**当**进入详情，
   **则**页面显示申请基本信息、申请人、目标资源、权限级别、访问截止日期、申请原因、风险等级、
   当前状态、创建时间和审批记录。
2. **前提**用户正在查看某条申请，**当**刷新页面，
   **则**页面恢复并展示同一申请，而不是返回列表或展示其他申请。
3. **前提**申请为 `High` 风险，**当**用户查看列表或详情，
   **则**风险具有比普通申请更明显的提示，并同时通过非颜色信息明确表达为高风险。
4. **前提**详情加载失败且允许重试，**当**错误发生，
   **则**页面显示明确错误状态和重试入口；申请不存在或不在可见范围内时显示明确且不泄露额外信息的状态。

---

### 用户故事 4：批准或拒绝权限申请（优先级：P1）

审批人需要基于申请详情处理分配给自己的 `Pending` 申请，并留下不可歧义的审批结果、处理时间以及
拒绝原因，以便申请人查看最终结果并形成可追踪记录。

**优先级说明**：审批决定完成 MVP 的端到端业务闭环，是系统替代聊天、邮件或表格流程的关键价值。

**独立测试**：分别准备两条 `Pending` 申请，一条批准、一条填写原因后拒绝；验证状态、审批记录、
申请人可见结果以及终态申请不可再次审批。

**验收场景**：

1. **前提**审批人正在查看分配给自己的 `Pending` 申请，**当**选择批准并确认成功，
   **则**状态变为 `Approved`，审批记录包含批准结果、审批人和处理时间，申请人能够看到最终结果。
2. **前提**审批人正在查看分配给自己的 `Pending` 申请，**当**尝试拒绝但未填写有效拒绝原因，
   **则**系统阻止拒绝并明确提示原因必填。
3. **前提**审批人已填写有效拒绝原因，**当**拒绝操作成功，
   **则**状态变为 `Rejected`，审批记录包含拒绝结果、审批人、拒绝原因和处理时间。
4. **前提**申请已经为 `Approved` 或 `Rejected`，**当**任意审批人查看或尝试再次处理，
   **则**页面清晰展示最终状态，且系统不允许产生第二次审批结果。
5. **前提**审批操作失败且申请仍为 `Pending`，**当**系统返回失败结果，
   **则**审批人看到明确反馈和重试入口，申请状态及审批记录保持不变。
6. **前提**当前演示员工是某条 `Pending` 申请的申请人，且可能同时是其他申请的负责审批人，
   **当**查看自己提交的申请，**则**能够查看详情，但不能批准或拒绝自己的申请。
7. **前提**一条 `Pending` 申请的访问截止日期不晚于当前日期，**当**审批人尝试批准，
   **则**系统阻止批准并说明期限已失效；审批人仍可填写原因后拒绝该申请。

### 边界情况

- 搜索词只有空白、包含特殊字符或大小写不一致时，系统必须将空白词视为未搜索，并把其他内容作为
  普通文本安全处理，不得导致页面错误。
- 搜索或筛选条件改变后，分页必须回到第 1 页；地址中的页码超过有效范围时，不得在仍有匹配数据的情况下
  显示误导性的空状态，而必须恢复到有效结果页。
- 地址包含未知或无效的状态、风险等级或页码时，页面必须使用明确的默认查询状态正常打开，并反映实际采用
  的查询条件。
- 当前用户没有任何可见申请与当前查询没有匹配结果时，必须显示语义不同的空状态。
- 申请详情在打开后被其他审批人处理时，后续审批尝试必须以最新状态为准，提示申请已处理，且不得覆盖首个
  有效审批结果。
- 多次或并发提交同一审批决定时，只能产生一个最终状态和一条有效审批结果记录。
- 访问截止日期不晚于提交日、拒绝原因只有空白或必填文本只有空白时，必须视为无效输入。
- 目标资源或其可用权限发生变化，导致当前组合不再具有风险映射时，必须阻止提交并要求申请人重新选择，
  不得使用默认风险等级继续创建申请。
- 目标资源没有审批候选员工、候选列表为空或列表中只有申请人本人时，必须阻止创建申请，不得生成无人负责或
  允许自审批的 `Pending` 申请。
- 数据加载或操作失败后重试时，系统必须保留仍然有效的查询条件、表单输入或审批上下文。
- 高风险提示在颜色不可见、高对比度环境或辅助技术下仍必须能够被识别为“高风险”。

## 需求（必填）

### 功能需求

- **FR-001**：MVP 必须提供多个可直接切换的预置演示员工身份；每个 `DemoUser` 必须具有稳定的唯一标识和
  显示名称，不得保存 Requester、Approver 或其他永久角色。身份切换不属于注册或登录流程。
- **FR-002**：对于任一申请，当 `request.requesterId` 等于当前员工 ID 时，该员工必须能够以 Requester 关系
  查看自己提交的申请；当 `request.approverId` 等于当前员工 ID 时，该员工必须能够以 Approver 关系查看分配
  给自己的待处理及已处理申请。两类可见申请必须合并且不得重复。
- **FR-003**：系统必须将申请状态限定为 `Pending`、`Approved` 或 `Rejected`，并展示清晰的中文状态含义。
- **FR-004**：申请列表中的每条记录必须展示申请人、目标资源、申请权限、风险等级、当前状态和创建时间。
- **FR-005**：用户必须能够按申请人名称或资源名称进行文本搜索；搜索必须支持名称的部分匹配。
- **FR-006**：用户必须能够分别按申请状态和风险等级筛选，并能将搜索与两个筛选条件组合使用。
- **FR-007**：申请列表必须提供分页，并清楚表达当前页、可继续浏览的方向以及是否还有更多结果。
- **FR-008**：搜索词、状态筛选、风险筛选和当前页必须由页面地址表达，并在刷新、浏览器前进后退和复制地址
  后恢复。
- **FR-009**：列表必须区分“当前用户没有任何申请”和“当前查询没有匹配结果”，并为后者提供清除或调整条件
  的操作。
- **FR-010**：创建申请必须收集目标资源、请求的权限级别、访问截止日期和申请原因，四项均为必填。
- **FR-011**：系统必须在提交前校验必填内容；访问截止日期必须晚于提交日。无效字段必须获得明确、可定位的
  错误提示，且无效申请不得创建。
- **FR-012**：提交期间必须显示进行中状态并阻止重复提交；成功和失败都必须提供明确反馈。
- **FR-013**：创建成功的申请必须获得可再次定位的唯一标识、创建时间、唯一负责审批人和 `Pending` 状态，
  并能够立即从列表及详情中查看。
- **FR-014**：每条申请必须具有且仅具有 `Low`、`Medium` 或 `High` 三种风险等级之一。
- **FR-015**：每个允许的目标资源与权限级别组合必须预先指定且仅指定一个 `Low`、`Medium` 或 `High`
  风险等级。系统必须使用该直接映射确定申请风险；未定义组合不得提交，且申请人不得修改映射结果。
- **FR-016**：详情必须通过申请的唯一标识恢复，并展示申请基本信息、申请人、负责审批人、目标资源、权限级别、
  访问截止日期、申请原因、风险等级、当前状态、创建时间和审批记录。
- **FR-017**：审批记录必须展示审批结果、审批人和处理时间；拒绝记录还必须展示拒绝原因。尚未审批时必须明确
  表示暂无审批记录。
- **FR-018**：只有当前员工 ID 等于申请 `approverId`，且不等于该申请 `requesterId` 时，才能处理这条
  `Pending` 申请；其他员工以及该申请的申请人均不得执行审批操作。
- **FR-019**：批准成功后，申请状态必须变为 `Approved`，同时新增且仅新增一条包含批准结果、审批人和
  处理时间的审批记录。
- **FR-020**：拒绝前必须收集去除首尾空白后仍非空的拒绝原因；拒绝成功后，申请状态必须变为
  `Rejected`，同时新增且仅新增一条包含审批人、原因和处理时间的审批记录。
- **FR-021**：`Approved` 和 `Rejected` 是不可再次审批的终态；并发处理只能接受第一个有效决定，后续尝试必须
  得到申请已处理的明确反馈。
- **FR-022**：`High` 风险必须在列表和详情中获得比 `Low`、`Medium` 更明显的视觉提示，并至少通过文本或图标
  与颜色共同表达。
- **FR-023**：申请列表和详情等异步数据界面必须提供 `Loading`、`Empty`、`Error` 和 `Success` 状态；创建提交
  和审批操作必须提供进行中、失败和成功状态。
- **FR-024**：发生允许重试的加载或操作错误时，系统必须提供明确的重试入口，并保留仍然有效的用户上下文；
  失败操作不得呈现为成功。
- **FR-025**：用户必须能够仅使用键盘完成列表查询、创建申请、打开详情以及批准或拒绝的核心流程，且当前焦点
  必须可感知。
- **FR-026**：表单控件和交互操作必须具有清晰名称；错误、状态、风险及操作结果不得仅依赖颜色传达。
- **FR-027**：页面地址只能包含恢复列表查询所需且允许分享的状态，不得包含申请原因、拒绝原因或其他敏感正文。
- **FR-028**：在同一浏览器演示环境中，申请、状态变化和审批记录必须由所有预置身份共享，并在页面刷新、
  关闭后重新打开及身份切换后保持不变。MVP 不要求这些数据跨浏览器或跨设备共享。
- **FR-029**：访问有效期必须从申请被批准时开始，到访问截止日期结束。批准时截止日期必须晚于批准日；
  截止日期已到或已过的 `Pending` 申请不得批准，但仍可按正常规则拒绝。
- **FR-030**：每个目标资源必须预先关联一个有顺序的审批候选员工列表。创建申请时，系统必须将申请的唯一
  `approverId` 确定为列表中第一位 ID 不等于 `requesterId` 的员工；不存在符合条件的员工时不得创建申请。
  预置 Demo 数据中每个资源的候选分配必须保证任一演示员工提交时都能选出另一名员工，避免正常演示进入
  无可用审批人或自审批场景。

### 关键实体

- **权限申请**：员工请求访问目标资源的业务记录；包含唯一标识、申请人、唯一负责审批人、目标资源、权限级别、
  访问截止日期、申请原因、风险等级、状态、创建时间和审批记录。
- **演示用户身份**：可被直接选择的预置企业员工基础身份；具有稳定的唯一标识和显示名称，不包含永久业务角色。
- **Requester 关系**：演示员工与单条权限申请之间的提交关系；当申请的 `requesterId` 等于员工 ID 时成立。
- **Approver 关系**：演示员工与单条权限申请之间的审批分配关系；当申请的 `approverId` 等于员工 ID 时成立。
- **目标资源**：被申请访问的系统、项目、数据资源或管理后台；决定可申请的权限范围，并关联有序审批候选员工列表。
- **资源权限规则**：一个允许申请的目标资源与权限级别组合；每个组合直接关联且仅关联一个风险等级。
- **审批分配规则**：目标资源与有序审批候选员工列表的关系；负责审批人是列表中第一位 ID 与申请人不同的员工。
- **审批记录**：一次有效最终决定的可追踪记录；包含批准或拒绝结果、审批人、处理时间，以及拒绝时必需的原因。
- **列表查询状态**：用于恢复列表含义的搜索词、状态筛选、风险筛选和页码；可通过页面地址分享和恢复。

### 业务规则

- 新申请的初始状态只能是 `Pending`，且只能发生一次 `Pending → Approved` 或 `Pending → Rejected` 转换。
- 访问有效期从批准时开始，到访问截止日期结束；截止日期不晚于提交日的申请无效，截止日期不晚于批准日的
  待审批申请不得批准。
- Requester 与 Approver 不是 `DemoUser` 的互斥或永久角色，而是相对于单条申请、分别由 `requesterId` 与
  `approverId` 确定的业务关系；同一员工可以是自己申请的 Requester，同时是其他申请的 Approver。
- 每条申请的 `requesterId` 与 `approverId` 必须不同，任何员工都不得审批自己提交的申请。
- 每条申请必须在创建时确定且仅确定一位负责审批人；审批人选择顺序由目标资源的预置候选列表决定，
  不由申请人选择，也不采用随机或轮流分配。
- 风险等级是申请的业务属性，不是由申请人自行声明的标签；每个允许的资源权限组合必须具有唯一且明确的
  风险映射，禁止通过计算猜测或默认值补全缺失映射。
- 拒绝原因是拒绝决定的一部分；没有有效原因的拒绝不是有效审批。
- 审批结果一旦生效，后续查看必须展示相同终态和审批记录，不得因刷新或身份切换而丢失。
- 同一浏览器演示环境中的业务数据必须具有连续生命周期，不得因页面刷新、关闭后重新打开或身份切换而重置。
- 列表查询条件采用“搜索条件与各筛选条件同时满足”的组合规则。

### 范围边界

本 MVP 明确不包含：

- 注册和登录系统；
- Admin 身份或管理功能；
- 完整的 RBAC 权限配置后台；
- 多级审批；
- 企业组织架构管理；
- 邮件或即时消息通知；
- 真实企业身份服务集成；
- 向第三方系统自动下发权限；
- 审计日志导出；
- 国际化；
- 移动端专用应用。
- 跨浏览器或跨设备共享演示业务数据。

本规格不为以上未来能力预留额外流程、Admin、RBAC、状态或配置入口。

## 成功标准（必填）

### 可衡量结果

- **SC-001**：核心端到端流程必须能够在不依赖开发者工具、手工修改持久化数据或页面外操作的情况下，
  仅通过用户界面完整完成“创建申请 → 查找申请 → 查看详情 → 切换到负责审批员工 → 批准或拒绝 →
  切回申请员工 → 查看最终结果”，并由真实 Chromium 浏览器端到端验收验证。
- **SC-002**：在目标资源、权限级别、截止日期和申请原因均已知时，用户必须能够在一个连续表单流程中
  完成有效申请，无需离开创建页面执行额外配置；提交成功后必须立即进入新申请详情，并确认其状态为
  `Pending`。
- **SC-003**：在包含至少 1,000 条可见申请的验收数据中，95% 的搜索、筛选和翻页操作在 2 秒内向用户展示
  新结果或明确状态。
- **SC-004**：针对搜索、状态筛选、风险筛选和分页的全部约定验收组合，页面刷新、浏览器前进后退以及复制
  地址重新打开的恢复结果必须达到 100% 一致。
- **SC-005**：批准、带原因拒绝和终态重复处理的验收场景必须 100% 产生正确状态与审批记录，且不得出现重复
  最终决定。
- **SC-006**：所有主要异步界面的验收检查必须 100% 覆盖适用的加载、空、错误和成功状态；允许重试的错误
  必须具有可发现的重试入口。
- **SC-007**：核心流程必须能够 100% 仅通过键盘完成；所有高风险申请在去除颜色信息后仍能被正确识别。
- **SC-008**：申请列表和详情页面必须直接、明确展示当前状态和风险等级；详情页面必须让当前员工无需展开
  隐藏区域即可识别当前可执行的下一步操作。`High` 风险、最终状态和关键下一步不得仅依赖颜色表达。
- **SC-009**：创建申请、批准和拒绝产生的全部业务状态，在同一浏览器演示环境内经过刷新、关闭后重新打开及
  身份切换后必须 100% 保持一致，并继续遵循各身份的可见范围。

## 假设

- MVP 提供演示员工身份、目标资源及其有序审批候选员工列表均已确定的预置数据，并允许直接切换当前身份；
  不负责身份验证、用户管理、Admin、RBAC、角色配置或审批候选列表管理。
- 同一浏览器演示环境是 MVP 业务数据的持续存在边界；不同浏览器或设备可以拥有相互独立的演示数据。
- 每个演示员工都可以创建申请；员工的可见范围是 `requesterId` 等于本人 ID 的申请与 `approverId` 等于本人
  ID 的申请之并集。
- 可申请的目标资源及其权限级别已经由业务侧提供，MVP 不包含维护这些选项的管理界面。
- MVP 使用已预先定义的资源权限目录；目录中的每个允许组合均已给出唯一风险等级，不包含风险评分、
  默认风险或维护映射的管理功能。
- 每条申请在 MVP 中只需要一名审批人作出一次最终决定，不存在会签、转交或多级审批。
- 所有参与者使用统一且明确展示的业务时间口径；创建时间和处理时间可被不同员工一致理解。
- 验收环境能够提供覆盖三种状态、三种风险等级、成功与失败路径的代表性数据。
