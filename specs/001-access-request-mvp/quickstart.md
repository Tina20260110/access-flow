# AccessFlow MVP 运行与验收指南

本指南用于实现完成后的本地运行和验收。领域约束见 [data-model.md](data-model.md)，数据操作与错误语义见
[contracts/data-access.md](contracts/data-access.md)，路由行为见 [contracts/routes.md](contracts/routes.md)。

## 前置条件

- Node.js `22.22+`
- npm（使用仓库唯一 lockfile）
- 支持 IndexedDB、现代 CSS 和原生语义控件的当前主流桌面浏览器

## 安装与启动

```bash
npm install
npm run dev
```

打开终端输出的本地地址。首次启动必须自动校验 seed 并初始化 Demo 数据；后续刷新和重新打开应读取同一
浏览器中的现有业务状态。

生产构建由 `npm run build` 验证，路由行为由 `npm run preview` 提供的 production preview 验证。部署到其他
静态托管环境时，托管服务必须把 `/requests/:requestId` 等未知服务器路径 fallback 到 `index.html`；`dist/`
本身不负责提供服务器侧 history fallback。

## 开发质量检查

```bash
npm run typecheck
npm run lint
npm run test
npm run build
npm run test:e2e
```

期望结果：

- `typecheck` 在 strict 模式下通过，业务代码无显式 `any` 或类型检查逃逸。
- `lint`、unit/integration tests 和 production build 全部通过。
- Playwright 核心闭环必须在真实 Chromium 中仅通过用户界面完成创建、查找、详情、切换负责审批员工、
  批准或拒绝、切回申请员工并查看最终结果；不得依赖开发者工具、手工修改持久化数据或页面外操作。
  失败时保留 trace 供定位。

## 手工验收 1：列表与 URL 恢复

1. 选择一个具有可见申请的 Demo 身份，进入 `/requests`。
2. 提交申请人或资源搜索，选择状态和风险筛选，再进入第 2 页。
3. 复制当前地址并刷新；使用浏览器后退和前进；在同一浏览器新页面打开复制地址。
4. 分别输入合法重复参数（如 `status=Pending&status=Approved`）和“第一个值无效、后续值合法”的重复参数
   （如 `status=unknown&status=Pending`），并覆盖 `q`、`status`、`risk`、`page`。
5. 输入单个无效 `status`、`risk` 或 `page` 参数。
6. 使用没有匹配结果的组合条件。

期望结果：

- URL 包含 `q`、`status`、`risk`、`page` 的非默认值，刷新和历史导航恢复相同查询。
- 重复单值参数只采用第一个值，后续值被忽略并规范化为单值 URL；若第一个值无效，即使后续值合法也按
  现有 invalid fallback 处理。无效值不破坏其他参数，越界页恢复到有效页。
- 无可见申请与无匹配结果显示不同空状态，错误重试不清除 URL。

## 手工验收 2：创建与持久化

1. 选择任一有效 Demo 员工身份并进入 `/requests/new`，准备已知的目标资源、权限级别、截止日期和申请原因。
2. 验证空字段、纯空白原因和不晚于今天的截止日期均不能提交。
3. 不离开创建页面执行任何额外配置，在同一个连续表单流程中选择有风险映射和合格审批人的资源权限组合，
   填写全部已知信息并提交申请。
4. 成功后立即进入新申请详情，直接确认 `Pending`、风险等级、负责审批人及 revision 对应的当前状态。
5. 刷新页面、关闭后重新打开应用，再切换其他 Demo 身份。

期望结果：

- 进行中状态阻止重复提交，失败保留输入；有效提交无需页面外配置，成功后立即进入新申请详情并确认
  `Pending`。
- 风险与资源权限规则一致，审批人是有序列表中第一位非申请人。
- 新申请跨刷新、重开和身份切换保持存在，并遵循当前身份的可见范围。

## 手工验收 3：批准闭环

1. 不使用开发者工具、手工修改持久化数据或页面外操作，仅通过 UI 以一名 Demo 员工新建一条访问截止日期
   晚于今天的申请。
2. 通过列表查找并打开申请详情，再通过 UI 切换到详情中 `approverId` 对应的员工，重新找到并打开该申请。
3. 批准申请并确认详情为 `Approved` 且只有一条批准记录。
4. 通过 UI 切回 `requesterId` 对应的员工，重新找到申请并查看最终结果。

期望结果：

- 审批期间按钮不可重复触发，成功后终态和审批记录同时出现。
- 终态申请不再显示可执行审批操作；申请员工能看到相同最终结果。
- 列表和详情直接显示状态与风险；详情无需展开隐藏区域即可识别当前下一步。
- High Risk、最终状态和关键下一步同时使用文字或其他非颜色信息，不仅依赖颜色提示。

## 手工验收 4：拒绝与过期

1. 打开 `approverId` 等于当前员工 ID 的另一条 `Pending` 申请。
2. 尝试用空白原因拒绝，再填写有效原因拒绝。
3. 对截止日期已到的 `Pending` seed 申请尝试批准，再选择拒绝。

期望结果：

- 空白拒绝原因被字段错误阻止；有效拒绝生成唯一 `Rejected` 记录。
- 到期申请不能批准，页面说明原因，但仍允许按正常规则拒绝。

## 自动验收：冲突与错误重试

运行完整 unit/integration suite：

```bash
npm run test
```

必须覆盖：

- 两个审批 command 持有同一旧 revision 时只有第一个成功，第二个得到 `CONFLICT` 并重取最终状态。
- 创建、批准、拒绝的确定性 transient failure 不改变持久化数据；UI 保留上下文并允许重试。
- 损坏或未知 schemaVersion 的持久化根文档进入错误状态，只有明确执行“重置 Demo 数据”才恢复。
- 资源权限缺少映射、没有合格审批人、自审批、非负责人审批和终态重复审批均被领域层拒绝。

## 无障碍验收

1. 不使用鼠标，仅用键盘完成列表查询、创建、打开详情和批准或拒绝。
2. 触发表单错误，确认 label、错误摘要、字段错误及焦点移动正确。
3. 触发 loading、成功、失败和冲突，使用辅助技术确认动态反馈可感知。
4. 确认列表和详情中的状态与风险直接可见，详情中的关键下一步无需展开隐藏区域即可识别。
5. 临时去除颜色信息，确认 High Risk、最终状态和关键下一步仍可识别。

期望结果：所有交互使用原生可聚焦控件，焦点可见且顺序合理；对话框支持 Escape 并恢复焦点；核心状态和
下一步无需展开即可理解，重要状态不只依赖颜色，错误通过 `aria-describedby`/`aria-invalid` 关联，动态反馈
不会沉默或重复播报。

## Demo 数据重置

1. 从 AppShell 触发“重置 Demo 数据”。
2. 在确认对话框中取消，验证数据不变。
3. 再次触发并确认，等待重置成功反馈。

期望结果：重置以一个事务替换完整 seed，恢复默认身份并导航到 `/requests`；刷新后仍是重置后的确定性数据，
不会出现空数据库或半初始化状态。

## 性能验收

SC-003 采用以下固定协议验收：

1. 运行 `npm run build` 和 `npm run preview`，使用真实 Chromium 打开 production preview。
2. 准备至少 1,000 条当前员工可见申请；等待应用首次启动和数据初始化完成，首次应用启动时间不计入本指标。
3. 对文本搜索、状态筛选、风险筛选、组合筛选和翻页五类代表性操作各执行 20 次。
4. 每次从用户提交查询操作开始计时，到新结果或明确的加载、空、错误、成功状态可见为止。
5. 汇总全部样本计算 P95；判定标准为 P95 ≤ 2 秒，并记录环境、样本数和结果以便复核。

jsdom 中的 1,000 条 fixture 测试只验证搜索、筛选、稳定排序和分页正确性，并帮助发现明显算法问题，不以
墙钟时间作为 SC-003 的正式证据。未出现真实浏览器测量超标前，不添加虚拟列表、复杂 memoization 或额外缓存层。
