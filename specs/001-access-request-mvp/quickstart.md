# AccessFlow MVP 运行与验收指南

本指南用于实现完成后的本地运行和验收。领域约束见 [data-model.md](data-model.md)，数据操作与错误语义见
[contracts/data-access.md](contracts/data-access.md)，路由行为见 [contracts/routes.md](contracts/routes.md)。

## 前置条件

- Node.js `22.22+`
- npm（使用仓库唯一 lockfile）
- 支持 IndexedDB、现代 CSS 和原生语义控件的当前主流桌面浏览器

## 安装与启动

```bash
npm install
npm run dev
```

打开终端输出的本地地址。首次启动必须自动校验 seed 并初始化 Demo 数据；后续刷新和重新打开应读取同一
浏览器中的现有业务状态。

## 开发质量检查

```bash
npm run typecheck
npm run lint
npm run test
npm run build
npm run test:e2e
```

期望结果：

- `typecheck` 在 strict 模式下通过，业务代码无显式 `any` 或类型检查逃逸。
- `lint`、unit/integration tests 和 production build 全部通过。
- Playwright 核心闭环通过；失败时保留 trace 供定位。

## 手工验收 1：列表与 URL 恢复

1. 选择一个具有可见申请的 Demo 身份，进入 `/requests`。
2. 提交申请人或资源搜索，选择状态和风险筛选，再进入第 2 页。
3. 复制当前地址并刷新；使用浏览器后退和前进；在同一浏览器新页面打开复制地址。
4. 输入无效 `status`、`risk` 或 `page` 参数。
5. 使用没有匹配结果的组合条件。

期望结果：

- URL 包含 `q`、`status`、`risk`、`page` 的非默认值，刷新和历史导航恢复相同查询。
- 无效值被独立规范化，不破坏其他有效条件；越界页恢复到有效页。
- 无可见申请与无匹配结果显示不同空状态，错误重试不清除 URL。

## 手工验收 2：创建与持久化

1. 选择任一有效 Demo 员工身份并进入 `/requests/new`。
2. 验证空字段、纯空白原因和不晚于今天的截止日期均不能提交。
3. 选择一个有风险映射和合格审批人的资源权限组合，提交申请。
4. 在详情确认 `Pending`、风险等级、负责审批人及 revision 对应的当前状态。
5. 刷新页面、关闭后重新打开应用，再切换其他 Demo 身份。

期望结果：

- 进行中状态阻止重复提交，失败保留输入，成功后进入新申请详情。
- 风险与资源权限规则一致，审批人是有序列表中第一位非申请人。
- 新申请跨刷新、重开和身份切换保持存在，并遵循当前身份的可见范围。

## 手工验收 3：批准闭环

1. 以一名 Demo 员工新建一条访问截止日期晚于今天的申请。
2. 切换到详情中 `approverId` 对应的员工，通过列表找到并打开该申请。
3. 批准申请，刷新并确认详情仍为 `Approved` 且只有一条批准记录。
4. 再次尝试审批或切回 `requesterId` 对应的员工查看最终结果。

期望结果：

- 审批期间按钮不可重复触发，成功后终态和审批记录同时出现。
- 终态申请不再显示可执行审批操作；申请员工能看到相同最终结果。
- High Risk 申请同时使用“高风险”文字和非颜色提示。

## 手工验收 4：拒绝与过期

1. 打开 `approverId` 等于当前员工 ID 的另一条 `Pending` 申请。
2. 尝试用空白原因拒绝，再填写有效原因拒绝。
3. 对截止日期已到的 `Pending` seed 申请尝试批准，再选择拒绝。

期望结果：

- 空白拒绝原因被字段错误阻止；有效拒绝生成唯一 `Rejected` 记录。
- 到期申请不能批准，页面说明原因，但仍允许按正常规则拒绝。

## 自动验收：冲突与错误重试

运行完整 unit/integration suite：

```bash
npm run test
```

必须覆盖：

- 两个审批 command 持有同一旧 revision 时只有第一个成功，第二个得到 `CONFLICT` 并重取最终状态。
- 创建、批准、拒绝的确定性 transient failure 不改变持久化数据；UI 保留上下文并允许重试。
- 损坏或未知 schemaVersion 的持久化根文档进入错误状态，只有明确执行“重置 Demo 数据”才恢复。
- 资源权限缺少映射、没有合格审批人、自审批、非负责人审批和终态重复审批均被领域层拒绝。

## 无障碍验收

1. 不使用鼠标，仅用键盘完成列表查询、创建、打开详情和批准或拒绝。
2. 触发表单错误，确认 label、错误摘要、字段错误及焦点移动正确。
3. 触发 loading、成功、失败和冲突，使用辅助技术确认动态反馈可感知。
4. 临时去除颜色信息，确认风险和状态仍能由文字识别。

期望结果：所有交互使用原生可聚焦控件，焦点可见且顺序合理；对话框支持 Escape 并恢复焦点；重要状态不只
依赖颜色，错误通过 `aria-describedby`/`aria-invalid` 关联，动态反馈不会沉默或重复播报。

## Demo 数据重置

1. 从 AppShell 触发“重置 Demo 数据”。
2. 在确认对话框中取消，验证数据不变。
3. 再次触发并确认，等待重置成功反馈。

期望结果：重置以一个事务替换完整 seed，恢复默认身份并导航到 `/requests`；刷新后仍是重置后的确定性数据，
不会出现空数据库或半初始化状态。

## 性能验收

使用至少 1,000 条可见申请的验收 fixture 运行列表集成场景，记录搜索、组合筛选和翻页从操作到新结果或明确
状态出现的时间。95% 操作必须在 2 秒内完成。未出现实际超标前，不添加虚拟列表、复杂 memoization 或额外缓存层。
