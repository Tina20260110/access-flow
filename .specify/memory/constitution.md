# Access Flow 项目宪章

## 核心原则

### I. 中文为项目工作语言（不可妥协）

本项目必须以中文作为需求分析、设计、实现说明、测试说明、代码审查和项目协作的默认工作语言。
所有新建或更新的 `spec.md` 文件必须使用中文编写，包括标题、需求描述、用户故事、验收标准、
边界条件和补充说明。后续生成的计划、任务、清单、报告及其他项目文档也必须默认使用中文。

源代码标识符、API 字段、命令、文件路径、协议名称、第三方产品名称和其他不宜翻译的技术内容
可以保留原文，但其上下文解释必须使用中文。只有在外部交付规范明确要求其他语言时，相关交付物
才可以使用其他语言，并且必须在对应文档中记录原因和适用范围。

将中文设为统一工作语言可以减少需求理解偏差，保证规格、实现与审查过程具有一致且可追溯的语境。

## 语言规范与例外

- 文档正文必须使用简体中文；首次出现且可能引起歧义的专业术语，可以附带原文。
- `spec.md` 中不得以整段外语正文替代中文内容；引用外部资料时必须同时提供中文说明或摘要。
- 代码、配置、数据格式及外部接口必须遵循其技术生态的命名规则，不得为了中文化而破坏兼容性。
- 自动生成内容在进入项目仓库前必须检查语言合规性；不符合本宪章的内容必须先完成中文化。
- 外语例外必须局限于确有必要的内容，不得扩展为整个文档或整个协作流程的默认语言。

## 开发与审查流程

1. 创建或更新功能规格时，作者必须确认 `spec.md` 全文以中文表达，并保持技术含义准确。
2. 从规格派生的计划、任务、测试说明和验收记录必须延续中文语境及术语。
3. 代码审查必须包含语言合规检查；发现非必要的外语正文时，不得通过审查，直至完成修正。
4. 若采用外语例外，审查者必须确认其符合本宪章规定，并已记录原因和适用范围。

## 治理

本宪章是项目语言与文档规范的最高约束；与其他项目约定冲突时，以本宪章为准。任何修订必须
记录变更内容、变更理由、受影响的工作产物及必要的迁移方式，并更新版本号和最后修订日期。

宪章采用语义化版本管理：删除或重新定义既有原则、造成治理规则不兼容时提升主版本号；新增原则
或实质性扩展约束时提升次版本号；仅澄清措辞、修正错误且不改变规则含义时提升修订号。

所有规格评审和代码审查都必须验证宪章合规性。若存在例外，必须在相应文档或审查记录中说明理由；
未经记录和审查的例外不具有效力。
