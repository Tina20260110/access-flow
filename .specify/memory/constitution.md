# AccessFlow 项目宪章

## 核心原则

### I. 严格类型安全

业务代码必须在严格类型检查下保持类型安全，禁止使用显式 `any`、双重断言或关闭类型检查来绕过
类型系统。类型尚不明确的数据必须先使用 `unknown` 表达，再通过收窄获得可用类型。

API 响应、用户输入、URL 参数、持久化数据、跨窗口消息和第三方 SDK 返回值等外部数据进入应用边界时，
必须经过明确的运行时校验或可靠的边界适配；类型断言不得替代数据校验。边界内的类型必须来源清晰，
并能够表达有效状态，避免用可选字段或宽泛联合类型掩盖无效状态。

### II. 清晰的组件与模块职责

组件和模块必须具有清晰、可描述的单一职责，其输入、输出和副作用必须可识别。非简单业务规则、
数据转换和流程编排必须与纯 UI 展示适当分离，使业务行为能够独立理解和测试；简单逻辑不得为了形式
被强行拆分。

发现稳定、真实且具有相同变化原因的重复时，必须优先复用现有能力。仅有表面相似或未来可能复用时，
禁止提前抽象；抽象本身必须降低总体理解和维护成本。

### III. 状态归属与生命周期

设计状态前必须区分其真实归属：服务端事实及其缓存属于 `server state`；可导航、可分享或需要恢复的
页面状态属于 `URL state`；短生命周期的交互状态属于 `local UI state`；确需跨功能长期共享且无法由
前述状态派生的数据才属于 `global client state`。

每个状态必须放在能够准确表达其生命周期的最小合理作用域。禁止仅为访问方便将状态提升为全局状态，
也禁止保存能够从现有来源可靠派生的重复状态。状态跨作用域提升时，technical plan 或变更说明必须记录
所有者、生命周期和提升理由。

### IV. 完整且可恢复的用户体验

所有异步数据界面必须明确处理 `loading`、`empty`、`error` 和 `success` 状态；适用时还必须处理刷新、
重试和过期数据。用户发起操作后必须得到及时且明确的进行中、成功或失败反馈，并避免无提示的重复提交。

筛选、搜索、分页、排序、标签页等可由 URL 安全表达且影响页面含义的状态，必须优先使用 URL 表达，
以支持分享、刷新恢复和浏览器前进后退。敏感信息和纯瞬时交互状态禁止写入 URL。

### V. 无障碍是交付要求

交互控件必须支持完成其核心操作所需的键盘使用，并具有可感知的焦点状态。实现必须优先使用语义化
HTML；只有原生语义无法满足需求时才可补充 ARIA，并必须保持名称、角色和状态准确。

重要信息、错误、成功和选中状态不得只通过颜色表达，必须同时提供文本、图标、形状或其他可感知线索。
表单控件必须具有可识别的标签，动态反馈必须能够被辅助技术感知。

### VI. 面向行为的测试

测试必须以业务行为、风险和关键用户流程为中心。复杂的纯逻辑必须优先使用单元测试验证；模块协作、
数据边界和核心用户流程必须具有适当的集成测试或端到端测试。缺陷修复必须包含能够复现并防止回归的测试。

测试不得以覆盖率数字本身为目标。覆盖率只能用于发现未检查区域，不能替代对关键行为、失败路径和
边界条件的验证，也不能通过无有效断言的测试提高数字。

### VII. 简单代码与依赖克制

实现必须选择满足当前需求的最简单、可读、可维护方案。禁止夹带与当前需求无关的大规模重构，禁止为
尚不存在且未进入 specification 的扩展需求预先设计。必要重构必须与目标变更直接相关，并保持可审查范围。

新增运行时或开发依赖必须具有现有代码无法以合理成本提供的明确价值。引入前必须评估维护状态、体积、
安全、许可、兼容性和替代方案，并在 technical plan 或变更说明中记录理由。

### VIII. 基于测量的性能治理

实现必须避免能够在代码审查中明确识别的不必要重复请求、重复计算、无界数据处理和大范围重新渲染。
请求去重、缓存和计算复用必须尊重数据一致性及状态所有权，不能以性能名义制造隐蔽的陈旧状态。

除明显缺陷外，性能优化必须由可复现的测量、性能预算或真实问题支持，并在优化前后验证效果。
禁止以未经验证的性能假设增加复杂度。

### IX. 规格驱动开发

任何改变业务行为、用户流程、公共接口、跨模块数据流或引入显著技术风险的非简单功能，必须在实现前
完成 specification、technical plan 和可执行 tasks。纯文案、无行为变化的小修正等简单变更可以简化流程，
但必须在变更记录中清楚说明目标。

specification 必须描述 WHAT 和 WHY，包括用户价值、范围、行为和可验证的验收标准，禁止写入无必要的
实现细节。technical plan 必须描述 HOW，包括架构决策、数据与状态边界、风险、测试和验证方式。
implementation 必须能够追溯至 specification 的验收标准及对应 tasks；无法追溯的实现不得合并。

### X. 中文为项目工作语言

项目沟通、需求、设计说明、测试说明、代码审查和项目文档必须默认使用简体中文。所有 `spec.md` 必须
使用中文编写；由其派生的 plan、tasks、清单和报告必须保持中文语境及术语一致。

源代码标识符、API 字段、命令、文件路径、协议名称、第三方专有名词和其他不宜翻译的技术内容可以保留
原文，但上下文解释必须使用中文。外部交付规范明确要求其他语言时，必须记录原因和适用范围。

## 技术决策边界

本宪章只规定长期工程约束，不预先指定 React 状态管理库、UI 库、数据请求库、测试框架或具体目录结构。
这些选择必须在相关功能或基础设施的 technical plan 中，根据需求、约束、团队能力和可验证证据作出，
并记录取舍。单次计划中的技术选择不得自动上升为全项目永久规则；永久规则必须通过宪章修订确立。

任何技术方案都不得以工具限制为由绕过类型安全、状态归属、用户体验、无障碍、测试或可追溯性要求。

## 开发与审查门禁

实现开始前，负责人必须判断变更是否属于非简单功能；属于时必须确认 specification、technical plan 和
tasks 已完成且一致。代码审查必须至少验证：

- 类型检查通过，业务代码中无类型逃逸，外部数据边界具有有效校验；
- 组件与模块职责清晰，业务逻辑分离和复用程度与实际复杂度相称；
- 状态分类、所有者、生命周期和作用域合理，不存在为方便而全局化的状态；
- 异步状态、操作反馈、URL 可恢复性及无障碍要求均已覆盖；
- 测试覆盖变更涉及的关键行为和失败路径，且测试层级与风险相称；
- 新依赖、性能优化和重构具有明确证据与范围说明；
- 非简单功能的实现和测试能够追溯到 specification 验收标准及 tasks。

违反任一适用门禁的变更不得合并。确有外部约束导致无法立即满足时，必须记录原因、风险、责任人和明确
的修复条件，并获得代码所有者批准；“实现方便”不构成例外理由。

## 治理

本宪章是 AccessFlow 工程实践的最高约束；与其他项目约定冲突时，以本宪章为准。任何修订必须提交
书面提案，说明变更内容、理由、受影响产物和必要的迁移方式，并经项目维护者审查批准后生效。

宪章采用语义化版本管理：删除或重新定义既有原则、造成治理规则不兼容时提升主版本号；新增原则
或实质性扩展约束时提升次版本号；仅澄清措辞、修正错误且不改变规则含义时提升修订号。

所有 specification、technical plan 和代码审查必须检查适用的宪章条款。审查者必须阻止不合规变更，
或确认例外已按本宪章记录和批准。项目必须在重大架构变更或宪章修订后复查相关工作流与存量约定，
避免文档、计划和实现持续偏离。
